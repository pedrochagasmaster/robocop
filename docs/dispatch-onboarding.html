Launch Impala Jobs you can walk away from.

Dispatch runs on the Hadoop Edge Node. You ssh in, go to the directory holding your SQL, and launch a Job. A detached runner owns the execution, so closing your terminal — or losing the VPN — does not kill the query. This page gets a new analyst from first access to a verified first Job.

What Dispatch does

Running a long Impala query by hand means holding an SSH session open, remembering which resource pool was not full, re-typing the same impala-shell incantation, and losing everything when the connection drops. Dispatch turns that into a Job: a described unit of work, persisted to disk as a manifest, executed by a runner that Dispatch detaches from your terminal, with a run log you can rejoin at any time from any session.

It is not a new query engine. Under the Job sit the same production-tested orchestrator scripts the team already trusted, with their queue-cycling retry loop and email notifications intact. Dispatch owns the description, the validation, the refusals, and the supervision — never the SQL execution itself.

Detached execution

The runner is not a child of your shell. Disconnect, reconnect from another machine, and dispatch shows the same Job still running.

One vocabulary

Every Job is exactly one Source and one Destination. Illegal combinations are refused before anything reaches the cluster.

Three front ends, one engine

TUI, CLI, and the Python notebook API share the same validation, Kerberos check, Advisor gate, capacity limit, and manifests.

Refusals are loud

No ticket, an expiring ticket, two Jobs already running, an illegal cell: Dispatch stops with a reason instead of failing halfway through the cluster.

Source × Destination

These two axes are the whole model. Choose the Source from what your SQL is; choose the Destination from what you need afterwards.

SqlTemplate is restricted to Table on purpose: monthly partitioned output is meant for downstream analytical use, not bulk CSV export. Table + Csv is decomposed by the runner into table creation followed by a separate CSV export — it never uses the old combined create-and-compress path, and the CSV it writes is uncompressed.

Where the CSV lands. Dispatch captures your launch-time working directory once, when it starts. Every CSV destination in that session resolves against that directory — not against the SQL file's location, and not against wherever you cd to later. cd to the right place before you launch.

1 · First access

The Release Operator has already deployed the shared tree and activated its runtime. You only run onboarding, once per account:

/ads_storage/dispatch/onboard.sh
export PATH="$HOME/.local/bin:$PATH"
which dispatch

Run it directly — not with source. Onboarding creates or repairs your private state under /ads_storage/$USER/.dispatch (config, jobs, telemetry), writes the thin ~/.local/bin/dispatch launcher, and updates your shell profile. It never creates a venv and never runs pip. If it prints the export PATH… line, run that one command; otherwise open a new SSH session.

Rerunning onboarding is safe at any time. It replaces a stale launcher without deleting your jobs, your configuration, or an old personal venv.

If onboarding says the shared runtime is missing or invalid, stop and send the exact output to a Release Operator. Do not run install.sh and do not run pip: analysts do not repair the shared runtime, and a hand-patched environment is the hardest failure to diagnose later.

2 · Daily workflow

  1. ssh to the Edge Node and cd to the directory holding your .sql files. This is also where CSVs will land.
  2. Make sure you have a Kerberos ticket: klist, and kinit if not. Dispatch refuses to launch with less than five minutes of ticket life remaining.
  3. Run dispatch for the interactive cockpit, or dispatch job … for a scripted launch.
  4. Launch, then leave. Come back with dispatch or dispatch job logs whenever you want to check on it.
Two Jobs at a time. Dispatch admits at most two simultaneously Running or Pending Jobs per analyst. A third is hard-refused — it does not queue silently behind the others. Cancel something or wait.

3 · Write the SQL

A SqlFile holds one statement: a single SELECT. Dispatch materialises the result for you, so the file should describe rows, not perform DDL.

SELECT
    dt,
    card_type,
    input_mode,
    count(*)      AS txn_cnt,
    sum(amount)   AS amount,
    sum(approved) AS approved
FROM aa_enc.events
WHERE dt BETWEEN '2026-01-01' AND '2026-01-31'
GROUP BY dt, card_type, input_mode

Use Download demo SQL in the navigation to get this file, then point a Job at it. Two habits prevent most expensive Jobs:

  • Always filter the partition column. An unfiltered scan of a partitioned table is the single most common way to fill a resource pool and get rejected. The Advisor flags it.
  • Never SELECT * without a filter. That is an error-severity Advisor finding, and clearing it requires an explicit acknowledgement.

Templates

A SqlTemplate is the same idea with two placeholders that Dispatch substitutes once per month over the range you give it:

SELECT dt, card_type, count(*) AS txn_cnt
FROM aa_enc.events
WHERE dt BETWEEN '{date_inicio}' AND '{date_fim}'
GROUP BY dt, card_type

Dates are YYYY-MM-DD. A range longer than thirteen months is an error-severity Advisor finding, not a suggestion.

4 · Your first Job

Do this once before touching real work, so you learn the flow without debugging your query at the same time.

The TUI shows every choice on screen and disables the illegal ones for you — the fastest way to learn what the fields mean.

cd /path/to/your/sql/files
dispatch
  1. Press N for the New Job wizard.
  2. Leave Source on SqlFile and Destination on Csv. Illegal destinations grey out automatically.
  3. Pick your file from the SQL picker (it lists the .sql files in the launch directory), or type the path.
  4. Leave Execution Queue empty — that is auto, and it cycles every pool until one accepts.
  5. Press P to preview the generated SQL. Read it. This is what actually runs.
  6. Press L to launch. If the Advisor reports errors you get a gate: read the findings, then confirm or go back and fix the SQL.
  7. You land back on the Overview. Press V to follow the log live.

Same Job, one command. This is what you script once a configuration is settled.

cd /path/to/your/sql/files

dispatch job launch --source SqlFile --destination Csv \
  --sql dispatch_demo.sql --table demo --yes

dispatch job list
dispatch job logs JOB_ID --follow
dispatch job wait JOB_ID --timeout 1800 --json

--yes is mandatory: it is the non-interactive stand-in for the TUI's launch dialog. Add --acknowledge-advisor only when the Advisor reports error-severity findings and you have read them.

Same Job from Jupyter on the Edge Node. The notebook API wraps the CLI, so nothing is skipped.

from dispatch.notebook import Dispatch

d = Dispatch(cwd="~/sql")

job = d.launch(source="SqlFile", destination="Csv",
               sql="dispatch_demo.sql", table="demo")
job.watch()          # live state and log tail until terminal
job.succeeded        # True
job.to_df()          # the Result, as a DataFrame

Every call is a real Job — manifest, detached runner, the two-Job cap, all of it. Expect minutes, not milliseconds. There is no faster unaudited tier.

5 · Check that it worked

All of these should be true. If any is false, go to Troubleshooting.

  • The Job reached state Succeeded in the TUI Overview, or dispatch job wait exited 0.
  • The CSV exists in the directory you launched from — uncompressed, named for the table you asked for.
  • The run log ends cleanly, with no classified error such as SYNTAX_ERROR, TABLE_NOT_FOUND, or MEMORY_LIMIT_EXCEEDED.
  • If you asked for a Table destination, the table exists in the schema you chose, under your EID prefix.
  • The notification email arrived, if you supplied a recipient.
You are onboarded when you can launch a Job, explain which Source and Destination it used, close your terminal without worrying, and find the log again afterwards.

Resource Pools

An Impala Resource Pool is the queue that governs concurrent query resources. Leaving the selection empty means auto: cycle every pool until one accepts the query, which is what you want almost always. Restrict it only when you know the shape of your query.

If you select several, they are tried in that cycle-priority order regardless of the order you clicked them.

What can stop a launch

These refusals happen before anything reaches the cluster. All of them are the tool working correctly.

  • No Kerberos ticket, or fewer than five minutes left. Press K to kinit from inside the TUI, then launch again.
  • Two Jobs already Running or Pending. The cap is per analyst and it is hard. Cancel one or wait.
  • An illegal Source × Destination cell. The TUI prevents it; the CLI refuses it with exit code 2.
  • Missing SQL file, or a bad date range. Fix the field the validation summary points at.
  • Advisor error-severity findings. You get the gate. Read the findings, then Y to launch as written or N to fix the SQL first.

Reference · non-interactive

CLI Cookbook

The dispatch job subcommands launch and supervise Jobs without opening the TUI. They reuse the same validation, Kerberos checks, Advisor gates, capacity admission, manifest persistence, telemetry, and detached-runner handoff — they simply never instantiate a Textual screen. python -m dispatch job … is identical.

Launch

cd /path/to/sql/files

# SqlFile -> Csv
dispatch job launch --source SqlFile --destination Csv \
  --sql query.sql --table report --yes

# SqlTemplate -> Table, one run per month across the range
dispatch job launch --source SqlTemplate --destination Table \
  --sql monthly.sql --schema aa_enc --table monthly_out \
  --start-date 2026-01-01 --end-date 2026-01-31 --yes

# ExistingTable -> Csv, no SELECT involved
dispatch job launch --source ExistingTable --destination Csv \
  --existing-table aa_enc.events_existing --yes

Supervise

dispatch job list

JSON output

Add --json to any subcommand for exactly one document on stdout. Everything else — warnings, progress, diagnostics — goes to stderr, so you can pipe stdout straight into jq.

dispatch job launch --source SqlFile --destination Csv \
  --sql q.sql --table out --yes --json
# {"job_id": "20260727T120000Z_abc123", "state": "Pending", "pid": null}

dispatch job list --json
# {"jobs": [{"id": "...", "state": "Running", "source": "SqlFile", ...}]}

dispatch job wait JOB_ID --json
# {"job_id": "...", "state": "Succeeded", "exit_code": 0, "timed_out": false}

Exit codes

CodeMeaning
0Successful command — and, for wait, the Job Succeeded.
1wait only: the Job completed unsuccessfully or was Cancelled.
2Invalid invocation, missing --yes or Advisor acknowledgement, or launch validation failure. Argparse usage errors also exit 2.
3Unknown, malformed, or unsafe Job ID.
4Operational refusal or failure: Kerberos, capacity, timeout, handoff, cancel.
Scripting the distinction that matters. Exit 2 means you asked for something invalid — the query never ran. Exit 4 means the request was valid but the environment refused it, so a retry may succeed. Exit 1 from wait means the query ran and failed: read the log, not the flags.

A scripted end-to-end run

#!/usr/bin/env bash
set -euo pipefail
cd /path/to/sql/files

job_id=$(dispatch job launch \
  --source SqlFile --destination Csv \
  --sql monthly_report.sql --table monthly_report \
  --queue adhoc_fast,adhoc --yes --json | jq -r .job_id)

echo "launched ${job_id}"

if dispatch job wait "${job_id}" --timeout 3600 --json | jq -e '.state == "Succeeded"' >/dev/null; then
  echo "done: $(ls -1 *monthly_report*.csv)"
else
  dispatch job logs "${job_id}" --lines 200
  exit 1
fi

Safety rules

  • Launches and cancellations never proceed silently: pass --yes.
  • Advisor error findings additionally require --acknowledge-advisor. There is no environment variable to make this automatic — that is deliberate.
  • Job paths that are missing, corrupt, symlink-escaped, or outside the jobs root are rejected with exit 3.

Telemetry commands

dispatch telemetry who --days 30
dispatch telemetry summary --days 30

Both read local JSONL. Nothing leaves the Edge Node. Set DISPATCH_TELEMETRY=0 to stop recording.

Reference · Python

Notebook API

dispatch.notebook runs and monitors Jobs from Jupyter — or any Python script — on the Edge Node. It wraps the dispatch job CLI, reached through Python objects instead of argv and exit codes. Same validation, same Kerberos check, same Advisor gate, same two-Job cap, same manifests, same detached runners.

Quick start

from dispatch.notebook import Dispatch

d = Dispatch(cwd="~/sql")            # where your .sql files live

# SQL written here, loaded straight into a DataFrame
df = d.sql("SELECT dt, count(*) AS c FROM aa_enc.events GROUP BY dt").to_df()

# a table you already have
d.table("aa_enc.events", limit=1000).to_df()

# or a Job from one of your files, watched while it runs
job = d.launch(source="SqlFile", destination="Csv",
               sql="monthly_report.sql", table="report")
job.watch()                          # live state and log tail, refreshed in place
job.succeeded                        # True
job.to_df()                          # the Result, as a DataFrame

d.jobs(state="Running")              # supervise everything else
Every call is a real Job. Validation, Kerberos, Advisor gate, two-Job cap, manifest, detached runner. Expect minutes, not milliseconds. There is deliberately no faster unaudited query tier, so do not write a loop that calls d.sql() per row.

Inline SQL

job = d.sql(
    "SELECT * FROM aa_enc.events WHERE dt = '2026-07-01'",
    destination="Csv",       # Csv (default), Table, or Table+Csv
    table=None,              # required for Table destinations
    queue="auto",
    wait_for_slot=300,       # wait up to 5 min for a launch slot instead of failing
)

sql() saves the text as Inline SQL in the Notebook workspace and launches it as an ordinary SqlFile Job. It submits immediately and returns the Job, so d.sql(...) alone starts work and d.sql(...).to_df() runs and fetches in one line. There is no lazy relation to chain onto, because Dispatch has no query planner to defer to.

The workspace exists so your working directory only ever receives files you asked for by name. Inline SQL and its Results live under Dispatch's directory, not yours.

# materialise a table instead of fetching rows
d.sql("SELECT ...", destination="Table", table="weekly_agg").wait()

Reference · pre-launch analysis

Advisor

Before a Job launches, the Advisor parses your SQL and checks it against the Impala optimization manual. It reports Findings: a rule id, a guideline reference, a severity, what it detected, and what to do about it. It is flag-only — it never rewrites your SQL and never silently changes what runs.

Severities

error

Something likely to be expensive or wrong. Launching anyway requires an explicit acknowledgement: Y at the TUI gate, or --acknowledge-advisor on the CLI.

warning

Worth reading before you launch, but not gated. Usually a missing filter or a naming rule.

info

A pattern that is sometimes justified. Shown so you can confirm it was intentional.

What it never does

It does not modify your SQL, choose a different pool, or refuse a launch on its own. The only gate is the error-confirm step, and you control it.

R01–R15 are evaluated against the parsed SQL. R16 is a form rule: it checks the destination table name you typed, not the query text. R17 and R18 apply to DDL.

The four that stop you

FindingWhy it is an errorFix
R01 select-star-unfilteredAn unbounded SELECT * reads every column of every partition. It is the fastest way to exhaust a pool.Name the columns you need and add a partition predicate.
R04 date-range-over-13-monthsRanges beyond thirteen months are almost always an accident, and the cost is linear in months.Narrow the range, or split it into several Jobs.
R07 dangerous-broadcast-hintBroadcasting a large table replicates it to every node and can take the query — and the pool — down.Remove the hint, or switch to a shuffle join.
R09 cartesian-productA join with no usable condition multiplies row counts instead of matching them.Supply the join condition. If it really is intentional, acknowledge it.
Acknowledging is a decision, not a formality. --acknowledge-advisor and the TUI's Y both mean "I read this and I am launching the SQL as written." The Job's manifest records that you did. If you find yourself acknowledging the same finding every day, fix the query instead.

Reading a Finding

Each Finding gives you four things: the rule id so you can look it up, the guideline reference back into the optimization manual, a detection line saying what was found and where, and a remediation line saying what to change. In the TUI the gate scrolls with ↑↓ and PgUp/PgDn; on the CLI they print to stderr before the refusal.

The full specification, including exactly what each rule matches, is docs/query-optimization-advisor-spec.md.

Reference · when it goes wrong

Troubleshooting

Fix the first concrete error, not the symptom after it. Most first-run problems are setup or Kerberos; most later problems are the query or the cluster. The run log under /ads_storage/$USER/.dispatch/jobs/ is the system of record — quote it when you ask for help.

Setup

dispatch: command not found

The launcher is in ~/.local/bin, which may not be on your PATH yet in this shell.

export PATH="$HOME/.local/bin:$PATH"
which dispatch

If which still prints nothing, rerun /ads_storage/dispatch/onboard.sh and keep the full output. Opening a new SSH session also works, because onboarding updates your shell profile.

Onboarding says the shared runtime is missing or invalid

Stop. Send the exact error to a Release Operator. Do not run install.sh, and do not run pip — analysts do not repair the shared runtime, and a hand-patched environment is much harder to diagnose than a missing one. Your existing jobs, configuration, and any old personal venv can stay where they are.

The launcher behaves strangely after an upgrade

Rerun /ads_storage/dispatch/onboard.sh. It replaces a stale launcher without deleting your jobs or configuration. Do not run it with source.

Kerberos

Dispatch refuses to launch: no ticket, or the ticket is about to expire

Dispatch requires a valid ticket with at least five minutes of life remaining, because a ticket that expires mid-Job fails the query after it has already consumed cluster resources.

klist          # check
kinit          # renew
klist          # confirm

Inside the TUI's New Job screen, K does the same thing without leaving the app.

The Job failed with AUTH_ERROR or an authorization exception

Either the ticket expired while the Job was running, or you do not have rights on the schema or table. Refresh with kinit and retry; if it recurs on the same table, it is a permissions question for your platform team, not a Dispatch problem.

Launch refusals

"Two Jobs already running"

The cap is two simultaneously Running or Pending Jobs per analyst, and it is a hard refusal — a third does not queue silently. Check what is running with dispatch job list --state Running, then wait or cancel one. From the notebook API, wait_for_slot= lets a call wait for a slot instead of failing immediately.

The destination I want is greyed out (or exit code 2 on the CLI)

You picked an illegal Source × Destination cell. SqlTemplate can only write a Table; ExistingTable can only write a Csv. Press M in the TUI to see the matrix.

Exit code 2 with no obvious cause

Exit 2 is always "the request was invalid" — most often a missing --yes, a missing --acknowledge-advisor when the Advisor reported errors, a SQL path that does not exist relative to the invocation directory, or a malformed date.

Exit code 3

The Job ID is unknown, malformed, or resolves outside the jobs root. Copy it from dispatch job list rather than retyping it; in the TUI, Y on Job Detail copies it exactly.

Exit code 4

An operational refusal or failure: Kerberos, capacity, a timeout, a handoff problem, or a failed cancel. The request was valid, so a retry may well succeed once the cause is cleared.

Jobs that fail

SYNTAX_ERROR

Impala rejected the SQL. Preview it first (P in New Job) — for a SqlTemplate, the preview shows the text after substitution, which is where placeholder mistakes become visible.

TABLE_NOT_FOUND

The source table or schema does not exist. Use the Impala Browser (B) to confirm the schema and the exact table name before relaunching.

MEMORY_LIMIT_EXCEEDED

The query needs more memory than the pool allows. Reduce its scope — tighter partition filter, fewer columns, aggregate earlier — or ask your platform team about the pool's limits. Retrying the same query unchanged will fail the same way.

Rejected by the pool, or "all pools busy"

Cluster capacity, not your Job. If you restricted the queue, widen it: leaving the selection empty (auto) cycles every pool until one accepts. Otherwise retry off-peak.

The Job is stuck in Running but nothing is happening

Run dispatch job list — it reconciles stale manifests before printing, so a Job whose runner died is corrected rather than reported as running forever. Then read the tail of the log with dispatch job logs JOB_ID --lines 200.

Results

The CSV is not where I expected it

Dispatch captures the launch-time working directory once, at startup, and resolves every CSV destination against it for the whole session. If you launched the TUI from your home directory, that is where the CSV is — not next to the SQL file. cd to the right directory before starting Dispatch.

I asked for Table + Csv and only got the table

The runner does the table first, then a separate CSV export. If the Job ended between the two, the table exists and the CSV does not. The log shows which stage failed; rerunning as ExistingTable → Csv exports what was already built instead of recomputing it.

No notification email arrived

Email is sent by the orchestrator scripts, not by the TUI. Check that you supplied a recipient — the field is prefilled from DISPATCH_EMAIL when that is set, and empty otherwise. Multiple recipients are comma-separated.

Reporting a problem

Include these four things and the diagnosis is usually immediate:

  • The Job ID (Y on Job Detail copies it).
  • The exact command or the Source × Destination you chose.
  • The last 50 lines of dispatch job logs JOB_ID.
  • The exit code, if you used the CLI.
Nothing is deleted. Finished Jobs leave the dashboard after seven days but stay in History, with their manifests and logs intact under /ads_storage/$USER/.dispatch/jobs/. You can always go back and read what actually happened.

Reference · vocabulary

Glossary

Dispatch uses these words precisely, in the interface, the logs, and this handbook. Where a common synonym is deliberately avoided, it is named — using the avoided word in a bug report usually means describing the wrong thing.

Job
One end-to-end execution: a Source and Destination pair plus the parameters needed to run it — schema, table name, recipient email, SQL path. Composed of one or more calls to Orchestrator scripts. Avoid: run, execution, task.
Source
The kind of SQL a Job is built from: SqlFile, SqlTemplate, or ExistingTable. Avoid: query type, mode, workflow.
Destination
Where a Job's result is materialised: Table, Csv, or Table + Csv. Avoid: output, target, sink.
Job state
The lifecycle stage: Pending, Running, Succeeded, Failed, or Cancelled. Avoid: status, phase.
Orchestrator script
One of the three production-tested scripts in scr/. They own the queue-cycling retry loop and the email notifications, and Dispatch treats them as a black box. Avoid: backend, runner, engine.
Resource Pool
An Impala queue managing concurrent query resources. Orchestrators cycle through a fixed list until one accepts the query. Avoid: queue, fila.
Edge Node
The gateway server providing access to the Hadoop cluster. It hosts the orchestrator scripts and Dispatch itself.
Analyst
Someone who runs Dispatch on an Edge Node to launch and supervise Jobs. Owns private configuration, jobs, logs, and telemetry under /ads_storage/<user>/.dispatch/; never installs dependencies or runs pip. Avoid: user, end user, operator.
Release Operator
The person who deploys Dispatch to an Edge Node and manages the shared runtime: verified dependency bundles, install.sh, activation and rollback. Distinct from an Analyst, who only runs onboard.sh. Avoid: admin, deployer, maintainer.
Advisor
The pre-launch static analysis that checks a Job's SQL against the Impala optimization manual and reports Findings. Flag-only: it never modifies or gates the SQL beyond the error-confirm modal. Avoid: linter, optimizer, rewriter.
Finding
One Advisor detection: a rule id, a guideline reference, a severity (error / warning / info), a detection line, and a remediation line. Avoid: violation, issue, error — "error" is reserved for the severity tier.
Manifest
The on-disk description of a Job under /ads_storage/<user>/.dispatch/jobs/. The TUI and CLI supervise Jobs by reading manifests and logs; it is the system of record.
Inline SQL
SQL authored in a notebook cell rather than a .sql file you keep. It produces an ordinary SqlFile Job; the file it runs from belongs to Dispatch, not to you. Avoid: query string, ad hoc query, snippet.
Result
The rows a completed Job produced, read back into Python from the CSV its Destination wrote. A Table-only Job has no Result. Avoid: output, dataset, result set.
Notebook workspace
The Dispatch-owned directory holding Inline SQL and Results for notebook-launched Jobs, so your working directory only ever receives files you named. Avoid: scratch, temp directory, cache.
Legacy GUI
The original Windows tool that prepared SSH commands. Removed at v1.0. Its Mode field conflated Source and Destination; that is why they are now two orthogonal axes.

Relationships worth memorising

  • A Job has exactly one Source and exactly one Destination.
  • A Job whose Destination includes Csv has exactly one Result; a Table-only Job has none.
  • An analyst may have at most two Jobs Running at once. A third is hard-refused; it does not queue.
  • A terminal Job stays in the active dashboard for seven days, then moves to History. It is never deleted.

O que o Dispatch faz

Rodar uma query longa no Impala na mão significa manter uma sessão SSH aberta, lembrar qual resource pool não estava cheio, redigitar o mesmo impala-shell de sempre e perder tudo quando a conexão cai. O Dispatch transforma isso em um Job: uma unidade de trabalho descrita, persistida em disco como manifesto, executada por um runner que o Dispatch desacopla do seu terminal, com um log de execução ao qual você pode voltar a qualquer momento, de qualquer sessão.

Não é um novo engine de query. Por baixo do Job estão os mesmos orchestrator scripts já testados em produção, com o laço de retry entre filas e as notificações por e-mail intactos. O Dispatch é dono da descrição, da validação, das recusas e da supervisão — nunca da execução do SQL em si.

Execução desacoplada

O runner não é filho do seu shell. Desconecte, reconecte de outra máquina e o dispatch mostra o mesmo Job ainda rodando.

Um vocabulário só

Todo Job é exatamente um Source e um Destination. Combinações ilegais são recusadas antes de qualquer coisa chegar ao cluster.

Três interfaces, um engine

TUI, CLI e a API de notebook compartilham a mesma validação, checagem de Kerberos, gate do Advisor, limite de capacidade e manifestos.

Recusas são explícitas

Sem ticket, ticket expirando, dois Jobs já rodando, célula ilegal: o Dispatch para com um motivo em vez de falhar no meio do cluster.

Esses dois eixos são o modelo inteiro. Escolha o Source pelo que o seu SQL é; escolha o Destination pelo que você precisa depois.

SqlTemplate é restrito a Table de propósito: saída mensal particionada existe para uso analítico posterior, não para exportação em massa de CSV. Table + Csv é decomposto pelo runner em criação da tabela e, depois, uma exportação de CSV separada — nunca usa o antigo caminho combinado de criar-e-comprimir, e o CSV que ele escreve não é comprimido.

Onde o CSV cai. O Dispatch captura o diretório de trabalho uma única vez, ao iniciar. Todo destino CSV daquela sessão é resolvido em relação a esse diretório — não em relação ao local do arquivo SQL, nem a onde você fizer cd depois. Faça cd para o lugar certo antes de lançar.

1 · Primeiro acesso

O Release Operator já implantou a árvore compartilhada e ativou o runtime. Você roda apenas o onboarding, uma vez por conta:

/ads_storage/dispatch/onboard.sh
export PATH="$HOME/.local/bin:$PATH"
which dispatch

Rode diretamente — não com source. O onboarding cria ou repara seu estado privado em /ads_storage/$USER/.dispatch (configuração, jobs, telemetria), escreve o launcher fino ~/.local/bin/dispatch e atualiza seu perfil de shell. Ele nunca cria venv e nunca roda pip. Se imprimir a linha export PATH…, rode esse comando; caso contrário, abra uma nova sessão SSH.

Rodar o onboarding de novo é seguro a qualquer momento. Ele substitui um launcher desatualizado sem apagar seus jobs, sua configuração ou uma venv pessoal antiga.

Se o onboarding disser que o runtime compartilhado está ausente ou inválido, pare e envie a saída exata ao Release Operator. Não rode install.sh e não rode pip: analistas não reparam o runtime compartilhado, e um ambiente remendado à mão é a falha mais difícil de diagnosticar depois.

2 · Fluxo diário

  1. Faça ssh no Edge Node e cd até o diretório com seus arquivos .sql. É também onde os CSVs vão cair.
  2. Garanta um ticket Kerberos: klist e, se preciso, kinit. O Dispatch recusa lançar com menos de cinco minutos de ticket restantes.
  3. Rode dispatch para o cockpit interativo, ou dispatch job … para um lançamento roteirizado.
  4. Lance e vá embora. Volte com dispatch ou dispatch job logs quando quiser conferir.
Dois Jobs por vez. O Dispatch admite no máximo dois Jobs simultâneos em Running ou Pending por analista. O terceiro é recusado de forma dura — ele não entra numa fila silenciosa atrás dos outros. Cancele algo ou espere.

3 · Escreva o SQL

Um SqlFile contém uma instrução: um único SELECT. O Dispatch materializa o resultado por você, então o arquivo deve descrever linhas, não executar DDL.

SELECT
    dt,
    card_type,
    input_mode,
    count(*)      AS txn_cnt,
    sum(amount)   AS amount,
    sum(approved) AS approved
FROM aa_enc.events
WHERE dt BETWEEN '2026-01-01' AND '2026-01-31'
GROUP BY dt, card_type, input_mode

Use Baixar SQL de demonstração na navegação para obter esse arquivo e aponte um Job para ele. Dois hábitos evitam a maioria dos Jobs caros:

  • Sempre filtre a coluna de partição. Um scan sem filtro em tabela particionada é a maneira mais comum de encher um resource pool e ser rejeitado. O Advisor sinaliza isso.
  • Nunca SELECT * sem filtro. Isso é um finding de severidade error, e passar por ele exige um reconhecimento explícito.

Templates

Um SqlTemplate é a mesma ideia com dois marcadores que o Dispatch substitui uma vez por mês ao longo do intervalo informado:

SELECT dt, card_type, count(*) AS txn_cnt
FROM aa_enc.events
WHERE dt BETWEEN '{date_inicio}' AND '{date_fim}'
GROUP BY dt, card_type

As datas são YYYY-MM-DD. Um intervalo maior que treze meses é um finding de severidade error, não uma sugestão.

4 · Seu primeiro Job

Faça isto uma vez antes de encostar em trabalho real, para aprender o fluxo sem depurar sua query ao mesmo tempo.

O TUI mostra cada escolha na tela e desabilita as ilegais por você — o jeito mais rápido de aprender o que os campos significam.

cd /caminho/para/seus/sql
dispatch
  1. Pressione N para o assistente New Job.
  2. Deixe Source em SqlFile e Destination em Csv. Destinos ilegais ficam desabilitados sozinhos.
  3. Escolha seu arquivo no seletor de SQL (ele lista os .sql do diretório de lançamento) ou digite o caminho.
  4. Deixe Execution Queue vazio — isso é auto, e cicla todos os pools até um aceitar.
  5. Pressione P para pré-visualizar o SQL gerado. Leia. É isso que vai rodar de fato.
  6. Pressione L para lançar. Se o Advisor reportar erros, aparece o gate: leia os findings e confirme, ou volte e ajuste o SQL.
  7. Você volta para a Overview. Pressione V para acompanhar o log ao vivo.

O mesmo Job, um comando. É isto que você roteiriza depois que a configuração está definida.

  --sql dispatch_demo.sql --table demo --yes

--yes é obrigatório: é o substituto não interativo do diálogo de lançamento do TUI. Use --acknowledge-advisor apenas quando o Advisor reportar findings de severidade error e você os tiver lido.

O mesmo Job a partir do Jupyter no Edge Node. A API de notebook envolve a CLI, então nada é pulado.

from dispatch.notebook import Dispatch

d = Dispatch(cwd="~/sql")

job = d.launch(source="SqlFile", destination="Csv",
               sql="dispatch_demo.sql", table="demo")
job.watch()          # estado e log ao vivo até o estado terminal

Toda chamada é um Job de verdade — manifesto, runner desacoplado, o limite de dois Jobs, tudo. Espere minutos, não milissegundos. Não existe uma camada mais rápida sem auditoria.

5 · Confira se funcionou

Tudo abaixo deve ser verdade. Se algo falhar, vá para Solução de problemas.

  • O Job chegou ao estado Succeeded na Overview do TUI, ou dispatch job wait saiu com 0.
  • O CSV existe no diretório de onde você lançou — sem compressão, com o nome da tabela que você pediu.
  • O log termina limpo, sem erro classificado como SYNTAX_ERROR, TABLE_NOT_FOUND ou MEMORY_LIMIT_EXCEEDED.
  • Se você pediu destino Table, a tabela existe no schema escolhido, sob o prefixo do seu EID.
  • O e-mail de notificação chegou, se você informou um destinatário.
Você está onboardado quando consegue lançar um Job, explicar qual Source e Destination ele usou, fechar o terminal sem preocupação e reencontrar o log depois.

O que pode barrar um lançamento

Estas recusas acontecem antes de qualquer coisa chegar ao cluster. Todas são a ferramenta funcionando corretamente.

  • Sem ticket Kerberos, ou menos de cinco minutos restantes. Pressione K para rodar kinit de dentro do TUI e lance de novo.

Saída JSON

Adicione --json a qualquer subcomando para exatamente um documento no stdout. Todo o resto — avisos, progresso, diagnósticos — vai para o stderr, então você pode canalizar o stdout direto para o jq.

dispatch job launch --source SqlFile --destination Csv \
  --sql q.sql --table out --yes --json
# {"job_id": "20260727T120000Z_abc123", "state": "Pending", "pid": null}

dispatch job list --json
# {"jobs": [{"id": "...", "state": "Running", "source": "SqlFile", ...}]}

dispatch job wait JOB_ID --json
# {"job_id": "...", "state": "Succeeded", "exit_code": 0, "timed_out": false}

Códigos de saída

CódigoSignificado
0Comando bem-sucedido — e, no wait, o Job terminou em Succeeded.
1Só no wait: o Job terminou sem sucesso ou foi cancelado.
2Invocação inválida, falta de --yes ou do reconhecimento do Advisor, ou falha de validação. Erros de uso do argparse também saem 2.

A distinção que importa em scripts. Saída 2 significa que você pediu algo inválido — a query nunca rodou. Saída 4 significa que o pedido era válido, mas o ambiente recusou, então uma nova tentativa pode funcionar. Saída 1 do wait significa que a query rodou e falhou: leia o log, não as flags.

Uma execução completa em script

#!/usr/bin/env bash
set -euo pipefail
cd /caminho/para/seus/sql

job_id=$(dispatch job launch \
  --source SqlFile --destination Csv \
  --sql monthly_report.sql --table monthly_report \
  --queue adhoc_fast,adhoc --yes --json | jq -r .job_id)

echo "lancado ${job_id}"

if dispatch job wait "${job_id}" --timeout 3600 --json | jq -e '.state == "Succeeded"' >/dev/null; then
  echo "pronto: $(ls -1 *monthly_report*.csv)"
else
  dispatch job logs "${job_id}" --lines 200
  exit 1
fi

Regras de segurança

  • Lançamentos e cancelamentos nunca acontecem em silêncio: passe --yes.
  • Findings de severidade error exigem, além disso, --acknowledge-advisor. Não existe variável de ambiente para automatizar isso — é deliberado.
  • Caminhos de Job ausentes, corrompidos, com escape por symlink ou fora da raiz de jobs são rejeitados com saída 3.

API de notebook

dispatch.notebook roda e monitora Jobs a partir do Jupyter — ou de qualquer script Python — no Edge Node. Ele envolve a CLI dispatch job, acessada por objetos Python em vez de argv e códigos de saída. Mesma validação, mesma checagem de Kerberos, mesmo gate do Advisor, mesmo limite de dois Jobs, mesmos manifestos, mesmos runners desacoplados.

Início rápido

from dispatch.notebook import Dispatch

d = Dispatch(cwd="~/sql")            # onde ficam seus arquivos .sql

# SQL escrito aqui, carregado direto em um DataFrame
df = d.sql("SELECT dt, count(*) AS c FROM aa_enc.events GROUP BY dt").to_df()

# uma tabela que você já tem
d.table("aa_enc.events", limit=1000).to_df()

# ou um Job a partir de um dos seus arquivos, acompanhado enquanto roda
job = d.launch(source="SqlFile", destination="Csv",
               sql="monthly_report.sql", table="report")
job.watch()                          # estado e log ao vivo, atualizados no lugar
job.succeeded                        # True
job.to_df()                          # o Result, como DataFrame

d.jobs(state="Running")              # supervisione o resto
Toda chamada é um Job de verdade. Validação, Kerberos, gate do Advisor, limite de dois Jobs, manifesto, runner desacoplado. Espere minutos, não milissegundos. Não existe, de propósito, uma camada de query interativa sem auditoria — então não escreva um laço que chama d.sql() por linha.

Referência · análise pré-lançamento

Advisor

Antes de um Job ser lançado, o Advisor faz o parse do seu SQL e o confronta com o manual de otimização do Impala. Ele reporta Findings: um id de regra, uma referência de diretriz, uma severidade, o que detectou e o que fazer a respeito. É apenas sinalização — nunca reescreve seu SQL e nunca altera silenciosamente o que roda.

Severidades

error

Algo provavelmente caro ou errado. Lançar mesmo assim exige reconhecimento explícito: Y no gate do TUI, ou --acknowledge-advisor na CLI.

warning

Vale ler antes de lançar, mas não barra. Normalmente um filtro faltando ou uma regra de nomenclatura.

info

Um padrão às vezes justificado. Mostrado para você confirmar que foi intencional.

O que ele nunca faz

Não modifica seu SQL, não escolhe outro pool e não recusa um lançamento por conta própria. O único gate é a confirmação de erro, e ela é sua.

Cada Finding entrega quatro coisas: o id da regra, para consulta; a referência de diretriz de volta ao manual de otimização; uma linha de detecção dizendo o que foi encontrado e onde; e uma linha de remediação dizendo o que mudar. No TUI, o gate rola com ↑↓ e PgUp/PgDn; na CLI, eles são impressos no stderr antes da recusa.

Referência · quando dá errado

Solução de problemas

Corrija o primeiro erro concreto, não o sintoma seguinte. A maioria dos problemas de primeira execução é setup ou Kerberos; a maioria dos problemas posteriores é a query ou o cluster. O log em /ads_storage/$USER/.dispatch/jobs/ é o sistema de registro — cite-o ao pedir ajuda.

Setup

dispatch: command not found

O launcher está em ~/.local/bin, que pode ainda não estar no seu PATH neste shell.

export PATH="$HOME/.local/bin:$PATH"
which dispatch

Se o which continuar sem imprimir nada, rode /ads_storage/dispatch/onboard.sh de novo e guarde a saída completa. Abrir uma nova sessão SSH também resolve, porque o onboarding atualiza seu perfil de shell.

O onboarding diz que o runtime compartilhado está ausente ou inválido

Pare. Envie o erro exato ao Release Operator. Não rode install.sh e não rode pip — analistas não reparam o runtime compartilhado, e um ambiente remendado à mão é bem mais difícil de diagnosticar do que um ausente. Seus jobs, sua configuração e qualquer venv pessoal antiga podem ficar onde estão.

O launcher se comporta de forma estranha depois de uma atualização

Rode /ads_storage/dispatch/onboard.sh novamente. Ele substitui um launcher desatualizado sem apagar seus jobs ou sua configuração. Não rode com source.

Kerberos

O Dispatch recusa lançar: sem ticket, ou ticket prestes a expirar

O Dispatch exige um ticket válido com pelo menos cinco minutos restantes, porque um ticket que expira no meio do Job falha a query depois que ela já consumiu recursos do cluster.

klist          # conferir
kinit          # renovar
klist          # confirmar

Dentro da tela New Job do TUI, K faz o mesmo sem sair do aplicativo.

O Job falhou com AUTH_ERROR ou uma exceção de autorização

Ou o ticket expirou durante a execução, ou você não tem permissão no schema ou na tabela. Renove com kinit e tente de novo; se repetir na mesma tabela, é uma questão de permissões para a equipe de plataforma, não um problema do Dispatch.

Recusas de lançamento

"Dois Jobs já em execução"

O limite é de dois Jobs simultâneos em Running ou Pending por analista, e a recusa é dura — o terceiro não entra numa fila silenciosa. Veja o que está rodando com dispatch job list --state Running e espere ou cancele um. Na API de notebook, wait_for_slot= faz a chamada esperar por uma vaga em vez de falhar de imediato.

O destino que eu quero está desabilitado (ou código 2 na CLI)

Você escolheu uma célula Source × Destination ilegal. SqlTemplate só escreve Table; ExistingTable só escreve Csv. Pressione M no TUI para ver a matriz.

Código 2 sem causa óbvia

Saída 2 é sempre "o pedido era inválido" — na maioria das vezes falta de --yes, falta de --acknowledge-advisor quando o Advisor reportou erros, um caminho de SQL que não existe em relação ao diretório de invocação, ou uma data malformada.

Código 3

O Job ID é desconhecido, malformado ou resolve fora da raiz de jobs. Copie-o de dispatch job list em vez de redigitar; no TUI, Y no Job Detail copia exatamente.

Código 4

Recusa ou falha operacional: Kerberos, capacidade, timeout, problema de handoff ou cancelamento falho. O pedido era válido, então uma nova tentativa pode funcionar depois que a causa for resolvida.

Jobs que falham

SYNTAX_ERROR

O Impala rejeitou o SQL. Pré-visualize antes (P no New Job) — para um SqlTemplate, o preview mostra o texto após a substituição, que é onde erros de marcador ficam visíveis.

TABLE_NOT_FOUND

A tabela ou o schema de origem não existe. Use o Impala Browser (B) para confirmar o schema e o nome exato antes de relançar.

MEMORY_LIMIT_EXCEEDED

A query precisa de mais memória do que o pool permite. Reduza o escopo — filtro de partição mais estreito, menos colunas, agregar antes — ou pergunte à equipe de plataforma sobre os limites do pool. Repetir a mesma query sem mudanças vai falhar igual.

Rejeitado pelo pool, ou "todos os pools ocupados"

É capacidade do cluster, não o seu Job. Se você restringiu a fila, amplie: deixar a seleção vazia (auto) cicla todos os pools até um aceitar. Caso contrário, tente fora do horário de pico.

O Job está preso em Running mas nada acontece

Rode dispatch job list — ele reconcilia manifestos desatualizados antes de imprimir, então um Job cujo runner morreu é corrigido em vez de aparecer rodando para sempre. Depois leia o fim do log com dispatch job logs JOB_ID --lines 200.

Resultados

O CSV não está onde eu esperava

O Dispatch captura o diretório de trabalho uma única vez, na inicialização, e resolve todo destino CSV contra ele pela sessão inteira. Se você abriu o TUI a partir do seu diretório home, é lá que o CSV está — não ao lado do arquivo SQL. Faça cd para o diretório certo antes de iniciar o Dispatch.

Pedi Table + Csv e só recebi a tabela

O runner faz a tabela primeiro e depois uma exportação de CSV separada. Se o Job terminou entre as duas etapas, a tabela existe e o CSV não. O log mostra qual etapa falhou; relançar como ExistingTable → Csv exporta o que já foi construído em vez de recalcular.

O e-mail de notificação não chegou

O e-mail é enviado pelos orchestrator scripts, não pelo TUI. Confira se você informou um destinatário — o campo é pré-preenchido a partir de DISPATCH_EMAIL quando definido, e fica vazio caso contrário. Vários destinatários são separados por vírgula.

Reportando um problema

Inclua estas quatro coisas e o diagnóstico costuma ser imediato:

  • O Job ID (Y no Job Detail copia).
  • O comando exato ou o Source × Destination escolhido.
  • As últimas 50 linhas de dispatch job logs JOB_ID.
  • O código de saída, se você usou a CLI.
Nada é apagado. Jobs finalizados saem do dashboard após sete dias, mas permanecem no History, com manifestos e logs intactos em /ads_storage/$USER/.dispatch/jobs/. Você sempre pode voltar e ler o que realmente aconteceu.

Referência · vocabulário

Glossário

O Dispatch usa estas palavras com precisão — na interface, nos logs e neste manual. Onde um sinônimo comum é deliberadamente evitado, ele é citado: usar a palavra evitada em um relato de bug geralmente significa descrever a coisa errada.

Job
Uma execução ponta a ponta: um par Source e Destination mais os parâmetros necessários — schema, nome da tabela, e-mail, caminho do SQL. Composto por uma ou mais chamadas a Orchestrator scripts. Evite: run, execução, tarefa.
Source
O tipo de SQL do qual um Job é construído: SqlFile, SqlTemplate ou ExistingTable. Evite: tipo de query, modo, workflow.
Destination
Onde o resultado de um Job é materializado: Table, Csv ou Table + Csv. Evite: saída, alvo, sink.
Estado do Job
A etapa do ciclo de vida: Pending, Running, Succeeded, Failed ou Cancelled. Evite: status, fase.
Orchestrator script
Um dos três scripts testados em produção em scr/. São donos do laço de retry entre filas e das notificações por e-mail; o Dispatch os trata como caixa-preta. Evite: backend, runner, engine.
Resource Pool
Uma fila do Impala que gerencia recursos de queries concorrentes. Os orchestrators ciclam por uma lista fixa até uma aceitar a query. Evite: queue, fila.
Edge Node
O servidor de acesso ao cluster Hadoop. Hospeda os orchestrator scripts e o próprio Dispatch.
Analista
Quem roda o Dispatch em um Edge Node para lançar e supervisionar Jobs. Dono da configuração, jobs, logs e telemetria privados em /ads_storage/<user>/.dispatch/; nunca instala dependências nem roda pip. Evite: usuário, end user, operador.
Release Operator
Quem implanta o Dispatch em um Edge Node e gerencia o runtime compartilhado: bundles verificados de dependências, install.sh, ativação e rollback. Distinto do Analista, que só roda onboard.sh. Evite: admin, deployer, mantenedor.
Advisor
A análise estática pré-lançamento que confronta o SQL de um Job com o manual de otimização do Impala e reporta Findings. Apenas sinaliza: nunca modifica nem barra o SQL além do modal de confirmação de erro. Evite: linter, otimizador, rewriter.
Finding
Uma detecção do Advisor: id da regra, referência de diretriz, severidade (error / warning / info), linha de detecção e linha de remediação. Evite: violação, issue, erro — "erro" é reservado para a severidade.
Manifesto
A descrição em disco de um Job, em /ads_storage/<user>/.dispatch/jobs/. O TUI e a CLI supervisionam Jobs lendo manifestos e logs; é o sistema de registro.
Inline SQL
SQL escrito em uma célula de notebook em vez de um arquivo .sql que você mantém. Produz um Job SqlFile comum; o arquivo do qual ele roda pertence ao Dispatch, não a você. Evite: string de query, query ad hoc, snippet.
Result
As linhas que um Job concluído produziu, lidas de volta para Python a partir do CSV que seu Destination escreveu. Um Job só de Table não tem Result. Evite: saída, dataset, result set.
Workspace de notebook
O diretório do Dispatch que guarda Inline SQL e Results de Jobs lançados de notebook, para que seu diretório de trabalho só receba arquivos que você nomeou. Evite: scratch, diretório temporário, cache.
GUI legada
A ferramenta Windows original que preparava comandos SSH. Removida na v1.0. Seu campo Mode confundia Source e Destination; por isso hoje são dois eixos ortogonais.

Relações que vale memorizar

  • Um Job tem exatamente um Source e exatamente um Destination.
  • Um Job cujo Destination inclui Csv tem exatamente um Result; um Job só de Table não tem nenhum.
  • Um analista pode ter no máximo dois Jobs em execução ao mesmo tempo. O terceiro é recusado; não entra em fila.
  • Um Job em estado terminal fica no dashboard ativo por sete dias e depois vai para o History. Nunca é apagado.
